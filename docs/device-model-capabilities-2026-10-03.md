# 先评估端侧模型，再选择 LeftBlank 场景

2026-10-03。**当前最值得试的是已有文本的主题整理、原文摘录和范围很小的只读查找。通用排版指令、Typst 生成、精确计算、图片/PDF 版式恢复不作为端侧模型的首发场景。** 这是本次实测后的产品判断，不是对所有 Apple 模型的结论。

## 先分清测的是什么

上一轮自然语言排版的 59/100 是规则加模型的整体结果，不能当作模型本身的能力分数。上一轮图片/PDF 导入使用 PDFKit/Vision，完全没有调用 Foundation Models。

这次研究程序直接调用 `SystemLanguageModel.default`，标签任务另外调用 `SystemLanguageModel(useCase: .contentTagging)`，不经过 LeftBlank 的关键词规则，也不修改文稿。没有使用 PCC、其他云模型、个人文稿或真实文稿库。工具调用只访问三个合成文稿记录或执行单词计数。

Apple 的端侧模型、PCC、Siri 和系统 Writing Tools 不能混为同一套能力。Apple 公布了多个端侧与云端模型档位；这不意味着应用里的 `SystemLanguageModel.default` 就能复现 Siri 的全部体验。此次记录的公开 API 没有提供具体权重型号或构建号，不能把成绩归给未确认的 Advanced 模型。[Apple 模型家族说明](https://machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models)

## 实际环境与评测范围

设备是 M4 Pro / 24 GiB，macOS 27.0（26A428），Xcode 27 / Swift 6.4。运行时报告：上下文 8,192 tokens，支持 guided generation、tool calling、vision，`reasoning` capability 为 false；中文、英文均在支持语言列表中。false 表示没有声明该框架能力，不等于完全不会推理。不能把这台 Mac 的能力和上下文大小推广到所有设备、macOS 26 或 iPad。[框架更新与运行时查询](https://developer.apple.com/videos/play/wwdc2026/241/)

实际完成 **176 次模型调用**：115 条基础探测、30 条扩展题材测试、12 条分类定义实验、18 条稳定复测、1 条额外越界检查。分类定义实验与稳定复测复用了题目，不是 176 个独立样本。所有请求使用新 session、temperature 0、每次最多 512 输出 tokens。

输入、提示词、原始结果、评分代码和逐项复核记录在 [研究目录](../design/device-capabilities/README.md)。客观分数由代码核对；开放标签、改写忠实度和代码语义由本次助手逐项复核，**没有独立人工盲评**。样本是自有合成材料，没有客户试用或生产分布数据。

## 能力地图

| 能力 | 实测 | 对 LeftBlank 的判断 |
| --- | --- | --- |
| 主题标签，专用 tagging 模型 | 基础 12、扩展 12、中文提示 6 例均有相关且可区分主题的标签；个别标签泛化或抓住了次要内容 | 最适合先做可编辑的标签建议；不能宣称 100% 生产准确率 |
| 固定文稿分类 | 基础 12/12；扩展 10/12；写清分类边界后，同一扩展集 12/12 | 少量明确类别有效；任意分类体系或含糊类别不能自动套用 |
| 从已知文字中找事实 | 严格字段 4/12；去掉预算值的货币后缀后，事实匹配 10/12 | 直接事实有用；“提议但未确认”两例均被误填成确认结果，不适合自动落表或执行操作 |
| 基于给定片段的问答 | 严格答案与证据 10/12；8 个可回答问题都找到正确事实；4 个无答案问题有 2 个不遵守空值格式 | 可以探索返回原文证据；不把流畅回答等同于可靠拒答或全库问答 |
| 摘录式摘要 | 12/12 输出都是原文句子；9/12 选齐要求的三个重点 | 适合章节预览/原文摘录；仍可能漏掉重要行动，不能承诺完整摘要 |
| 同语言精简改写 | 9/12 经语义复核保留含义与语言；只有 6/12 同时忠实且更短 | 暂缓主推；出现新增责任归属、额外句子、中文变英文 |
| 两个只读工具的选择与参数 | 12/12 路由正确，两个计数参数均精确；最终字符串格式仅 6/12 严格正确 | 可以做很窄的查询助手；展示实际工具结果，不能依赖模型自由文本里的 ID |
| 生成 Typst | 10/12 能编译；逐项检查完整要求后 0/12 完成 | 不选择。Markdown/伪语言经常被当普通文字渲染，编译成功会掩盖失败 |
| 精确计算 | 4/12 正确；仅简单加法、乘法正确，多步折扣/税费及大整数错误 | 交给程序计算，不让模型算数 |
| 直接看文档截图 | 1/6 回答正确：双栏数量；四个中文标题均读错，表格总价也读错 | 不用它替代 OCR 或读取精确表格值；该探测没有接入 OCRTool |

这些任务评分口径不同，不合成一个“模型总体准确率”。分类题更容易，标签相关性带有主观判断，摘要题主要只有两种会议模板。高分只支持继续做小实验。

### 成功的例子

输入一段数据库连接池笔记，中文提示的标签输出为 **“数据库连接池、服务端资源管理、空闲连接回收”**。历史文章能输出 **“丝绸之路、贸易路线、文化交流”**，即使文件名、次要比喻或引用文本提到了其他主题。

明确分类边界后，小说归 `other`、排版讨论归 `writing`、历史文章归 `other`、真实行程归 `travel`。分类定义和中文标签的 18 条复测返回与前次相同的内容。这证明了这批固定题目的稳定性，仍不证明真实流量中的鲁棒性。

摘录式摘要可以返回完整原句，应用可以直接校验原文包含该句并定位到源码。即使选择不是最完整，结果的来源仍然可检查，比让模型自由重述整个章节更容易控制。

### 必须保留的失败证据

- 输入明确说“提议让周航负责，预算可能 200 元，建议某日完成，尚未决定”，模型仍把负责人、预算、日期全填出来。不能把 `String` 或 JSON 字段存在当成事实已确认。
- 中文改写从“尚未检查段落顺序”补成“责任归周航”，原文没有这一责任关系。
- 中文“我们不会把文稿上传到云端”被整体改成英文，违反同语言要求。
- 表格截图总价是 32.00，图像模型回答 22.00；清晰中文标题也产生漏字和错字。
- Typst 表格请求返回 Markdown 管道表格，编译后只显示一串普通文本；A4 请求返回伪语言代码块。

## 这次还学到了什么

**明确任务和输出语义，比把输出放进 schema 更重要。** 分类边界一开始没有解释清楚，小说和历史的标签存在分歧；补充定义后，同一批题目由 10/12 提升到 12/12。这是提示设计实验，已经看过这些题的结果，不能把提升当作新的独立验证。Apple 同样建议短而明确的目标、拆分复杂任务，并指出复杂条件可能超出小模型能力。[官方提示设计指南](https://developer.apple.com/documentation/foundationmodels/prompting-an-on-device-foundation-model)

**专用适配模型值得单独测。** 内容标签不是让通用模型回答问题，而是使用 tagging use case 分组文本。英文提示处理中文时，部分结果仍返回中文；中文明确提示的 6 个标签任务及其复测输出相关且符合语言要求。未来应按目标语言和类型设计 schema，而非给所有能力套同一个通用 prompt。[内容标签模型说明](https://developer.apple.com/documentation/foundationmodels/categorizing-and-organizing-data-with-content-tags)

**上下文大小不能凭旧文档写死。** 最初想制造越界的样本实际只有 8,001 输入 tokens，仍在本机 8,192 上下文内，返回了 DONE；它没有测试长文事实记忆。补充的 40,001 输入 tokens 被明确拒绝，错误指出总量 40,104 超过 8,192。指令、schema、工具和输出都占预算，真正的文稿功能应分段、查询运行时预算，避免把整本书塞进一个 session。

**Apple 的能力说明是起点，不是我们功能的验收成绩。** 官方把摘要、提取、文本理解、改写、分类和标签列为适合任务，同时提示避免依赖端侧模型做代码、数学与复杂逻辑。本次看到的代码和计算失败与这一边界一致；提取、改写同样要针对自己的约束验收。[官方能力说明](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models)

本次墙钟耗时包含了三次 token-count 查询，不能直接对比上一轮 app 服务的延迟。普通文本任务中位数约 0.45–1.3 秒；代码任务 p95 约 8 秒，近满上下文约 10 秒。未测冷启动、能耗、热压力或编辑器输入延迟。

## 按能力重新选场景

### 1. 文稿主题标签建议：第一候选

选一个章节或明确选择一段正文，生成 2–3 个主题标签，展示为可删除、可修改的建议。目的很具体：让文稿更容易整理和找回。使用 contentTagging、新 session、小输入；不会自动改正文、挪文稿或改变目录。分类结果含糊时允许不归类，不把任意标签等同于固定文件夹。

它容忍一个标签不够好，也容易让用户判断，而且本次跨题材与中文复测有直接支持。下一步只需做实际文稿的标签质量实验，记录“有用、重复、泛化、误导”，不需要先完成通用聊天、排版 agent 或 PCC。

### 2. 章节预览卡片：第二候选

每章选 2–3 句原文作为预览，附原始位置，点击回到文稿。先做摘录，不做自由改写；通过代码保证每一句都来自对应 revision 的正文。可以在查找旧稿时快速判断这章是否相关。

它的价值取决于选句能否帮助浏览，而非摘要是否像人写的。需要增加不同体裁的文章和重要限制容易遗漏的样本；本次会议模板不能作为完整摘要的生产验证。

### 3. 有界的只读文稿查找：后续候选

把“找我写过的数据库连接池笔记”映射到实际搜索工具，展示工具返回的真实文稿和命中句。只给模型少量、定义清楚的只读工具，结果由应用按真实 ID 渲染；不要让自由生成的文本决定打开、移动或修改什么。

两个合成工具上的 12/12 路由只能证明小实验可行。还要测试真实索引、同名文稿、找不到答案、中文别称、复合查询和来源导航。它不等于 Siri 已支持 LeftBlank，也不等于整库 RAG 已经可靠。

**目前优先评估第 1 项，保留第 2 项作为备选。** 现有排版与单页重建代码留在草稿 PR 供复核，不继续扩展或按可发布能力宣传。PCC 的效果另行评估，不能预先假定换云模型就能修复这些问题。
